# Diagnostic et correction
Sources principales : https://oca.github.io/OpenUpgrade/070_migration_files.html et https://oca.github.io/OpenUpgrade/080_migration_script_development.html (consultées le 2026-10-10).
Avant une correction, lire les fichiers disponibles openupgrade_analysis.txt et openupgrade_analysis_work.txt, puis les scripts pre/post/end concernés. Jusqu'à 13, chercher dans les migrations du module; à partir de 14, dans openupgrade_scripts/scripts/<module>/. Tenir compte des modifications noupdate et de l'ordre des phases. Les actions actuelles ne permettent pas de lire un fichier XML : ne pas prétendre l'avoir inspecté; arrêter si cette lecture est indispensable au diagnostic.
Privilégier les fonctions adaptées d'openupgradelib et les exemples officiels existants. Un essai limité à un module ne suffit pas à valider la migration complète. Chaque nouvel essai du moteur doit repartir d'une copie restaurée; ne jamais poursuivre une base partiellement modifiée comme si elle était un checkpoint validé.
Sur erreur transitoire réseau, essayer retry, au maximum deux fois sans progrès.
Sur traceback d'un script OpenUpgrade existant, lire le fichier puis ses dépendances pertinentes avec read_source. Proposer une correction minimale avec patch_script, qui ne s'exécutera que dans le conteneur de migration isolé. Chaque modification conserve avant/après et sa raison. La syntaxe est contrôlée puis un nouvel essai repart du checkpoint.
Le code Python corrigé peut modifier des données : préserver l'intention comptable et les relations métier. Ne pas masquer les exceptions ou supprimer des enregistrements pour satisfaire les tests. N'ajouter aucun accès réseau, lancement de processus, code encodé, lecture de secrets ou accès hors du filestore de travail.
Les tables de couverture, le moteur, ses validations, les manifests et Dockerfiles ne sont pas modifiables par ces actions.
Sur dépendance système manquante, code source non disponible, corruption, espace disque insuffisant ou écart métier inexpliqué, retourner stop avec une explication. Ne jamais boucler sans limite.
